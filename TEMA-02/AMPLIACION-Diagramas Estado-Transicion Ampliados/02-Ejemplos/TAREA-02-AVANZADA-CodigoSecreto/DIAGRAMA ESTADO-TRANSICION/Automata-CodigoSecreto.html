Autómata del código secreto

Caso práctico

Carlos tiene que programar el juego del código secreto (TAREA-02 AVANZADA). Antes de escribir una línea, María le pide el diagrama de estado-transición ampliado y las tablas del autómata. —Así sabrás qué páginas hay, qué botón se puede pulsar en cada una y qué hay que comprobar antes de cambiar de página. Y lo que es más importante en un juego: dónde no te puedes fiar de lo que manda el navegador.

Este documento aplica el método de los diagramas de estado-transición ampliados a la tarea TAREA-02-AVANZADA-CodigoSecreto. La solución (../SOLUCION-01/index.php) está programada a partir de este autómata: las constantes ST0…ST4 y EE0…EE6, el array $automata y un case por transición.

2.- El problema, en resumen

  • Se configura la partida: posiciones (4 o 5), colores (6, 7 u 8), intentos (6 a 12) y si los colores se pueden repetir.
  • El servidor elige un código secreto que no se envía a la página: se calcula cada vez a partir de una semilla con hash_hmac() y una clave que solo conoce el servidor.
  • En cada intento se eligen los colores; el servidor contesta con las negras (color y posición bien) y las blancas (color bien, posición mal).
  • Una pista por partida enseña el color de una posición y cuesta un intento. El jugador también se puede rendir.
  • La partida termina ganada (acierta el código) o perdida (sin intentos o rendido); el marcador se conserva entre partidas.

3.- Análisis

  • Eventos entrantes. La carga sin parámetros y un botón por acción: Empezar, Probar, Pista, Rendirse, Nueva partida y Cambiar la configuración. Todos llegan en el campo evento (<button name="evento" value="probar">).
  • Estados. Cuatro situaciones en las que la página espera algo distinto, más ST0: la configuración, el juego, la partida ganada y la partida perdida. Ganada y perdida admiten los mismos eventos, pero la página es distinta y el marcador también: son dos estados.
  • Variables de estado. La configuración, la semilla, los intentos hechos ("0123-4512"), la pista y el marcador. El código secreto no es una variable de estado: es una acción (AC4) que se repite en cada petición. Por eso se puede ver el código fuente de la página sin hacer trampas.
  • Dónde está la desconfianza. En ST2 llegan la configuración, la semilla y los intentos en campos ocultos. PL1 comprueba que son una partida posible en ese estado: configuración válida, intentos bien formados, ninguno acertado (si no, la partida ya habría terminado) y que quedan intentos.
  • Un predicado que se evalúa después de una acción. PL4 ("era el último intento") se evalúa después de añadir el intento (AC6). AC6 se hace en todos los caminos con PL2, así que no cambia el resultado de los otros predicados.

6.- Del autómata al código

//                Carga Empezar Probar Pista Rendirse Nueva Configurar
$automata = [
    ST0 => [1, 1, 1, 1, 1, 1, 1],
    ST1 => [1, 2, null, null, null, null, null],
    ST2 => [1, null, 3, 4, 5, null, null],
    ST3 => [1, null, null, null, null, 6, 7],
    ST4 => [1, null, null, null, null, 6, 7],
];
switch ($automata[$estado][$evento] ?? 1) {   // null ("---") se trata como T1
    case 3:                                   // ---- T3: ST2 + Probar
        $partida = leerPartida($_POST);       // AC1
        $pl1 = partidaValida($partida);       // PL1
        ...
        $secreto = codigoSecreto($partida);   // AC4
        [$intento, $motivo] = leerIntento($_POST, $partida);   // AC5
        $pl2 = $intento !== null;             // PL2

Tres decisiones que salen del autómata:

  • El código secreto es una acción, no una variable de estado. codigoSecreto() (AC4) hace mt_srand(crc32(hash_hmac('sha256', semilla, CLAVE))) y baraja: con la misma semilla da siempre el mismo código, y sin la clave no se puede calcular.
  • En ST1 solo se guarda el marcador. El formulario de configuración tiene campos posiciones, colores... Si AC10 escribiera también campos ocultos con esos nombres, el navegador mandaría los dos y PHP se quedaría con el último (el oculto): la configuración elegida no serviría de nada.
  • default junto a case 1. Durante la construcción paso a paso, una transición de la tabla que todavía no está programada se comporta como T1 en lugar de dejar la página en blanco.

7.- Pruebas: un camino por fila

Las 51 peticiones de pruebas.json (en fuentes-pasos) recorren todas las filas de la tabla de transiciones. Con la semilla 1, 4 posiciones, 6 colores y sin repetir, el código es rojo, morado, verde, naranja:

T2 !PL0 posiciones 6, colores 9, intentos 20 tres errores, sigue en ST1
T2 PL0 4, 6, 10, semilla 1 ST2, 10 intentos
T3 PL1 && !PL2 una posición sin color; dos colores iguales aviso, sigue en ST2
T3 ... && !PL4 rojo, verde, azul, amarillo "1 negras y 1 blancas.", quedan 9

  • Cambia la pista para que no cueste un intento pero solo se pueda pedir a partir del tercer intento. ¿Qué filas de la tabla de transiciones cambian?

Autoevaluación
  • ¿Por qué el código secreto no es una variable de estado? Porque viajaría en la página y se podría leer con el código fuente. Se calcula en cada petición (AC4) a partir de la semilla y de una clave que solo tiene el servidor.
  • ¿Por qué ganada y perdida son dos estados si admiten los mismos eventos? Porque la página que se muestra es distinta (ES3 y ES4) y lo que se ha sumado al marcador también. Un estado es una situación de la página, no solo los eventos que admite.
  • ¿Qué pasa si en ST2 llegan los intentos "0514" con la semilla 1? Ese intento es el código secreto: la partida ya habría terminado. PL1 es falso y se vuelve a la configuración (T3, primer camino).
  • En T3, ¿por qué PL3 se comprueba antes que PL4? Porque si el último intento acierta, la partida se gana: con el orden contrario, se perdería una partida ganada.
